# 基于大语言模型的招聘文本结构化抽取：Prompt 设计与稳健性分析

> 对应论文章节：**3.6 Prompt 设计与结构化提取方法** / **3.8 Prompt 性能比较与稳健性分析**
> 实验数据：`company_jobs_merged.csv`（3471 条岗位记录）
> 实验日期：2026-08-13

---

## 摘要

本实验以 3471 条真实招聘记录为总体，经清洗与分层抽样构建 20 条评测集，人工标注 200 个字段级标准答案，设计 v1.0 / v2.0 / v3.0 三版渐进式 Prompt，共采集 108 条模型输出，经 JSON 解析与 Schema 校验后与标准答案自动比对。结果显示：从零样本基线到「Few-shot + 强约束 + 自检」，字段级提取准确率由 **78.5% 提升至 98.0%**，信息单元级幻觉率由 **8.05% 降至 0.00%**，JSON 严格有效率由 **5.0% 升至 100.0%**，三次重复运行的输出一致率由 **57.5% 升至 100.0%**，代价是平均 Token 消耗增加约 **2.2 倍**。误差分析表明，**软技能字段是幻觉的主要来源（占 v1 全部幻觉的 60.6%）**，其成因是模型把「岗位职责」描述改写为「能力要求」；而 **AI 技术栈字段的主要问题不是幻觉而是边界误判**，即把大数据技术与 NLP 任务名错误归入 AI 技术栈。

## 一、实验设计总览

### 1.1 技术路线

```
company_jobs_merged.csv（3471条）
        ↓ ① 清洗（编码修复/去重/长度过滤/乱码过滤）
     1200 条候选
        ↓ ② 分层抽样（AI技术岗 / 非AI技术岗 / 非技术岗）
      20 条评测集
        ↓ ③ 人工标注 Ground Truth（规范 + 二次复核 + 歧义裁定）
   200 个字段级标准答案
        ↓ ④ 三版 Prompt 设计（v1.0 → v2.0 → v3.0）
        ↓ ⑤ 批量调用大语言模型
   108 条原始输出（主实验60 + 稳定性子实验48）
        ↓ ⑥ 三级 JSON 解析 + Schema 合法性校验
        ↓ ⑦ 归一化 + 别名表 + 可接受答案集 → 与 GT 自动比对
        ↓ ⑧ 幻觉两阶段判定（自动证据检索 + 人工裁定）
   ┌────────┬────────┬────────┬─────────┐
准确率   幻觉率   Token/耗时  JSON有效率
        ↓ ⑨ 重复运行（3次）→ 输出一致率
        ↓ ⑩ Temperature 敏感性实验（协议与脚本，见 §7）
     Prompt 优化结论
```

### 1.2 实验规模

| 项目 | 数量 |
|---|---|
| 原始记录 | 3471 |
| 清洗后候选 | 1200 |
| 评测集样本 | 20（A 层 AI 技术岗 8 / B 层非 AI 技术岗 6 / C 层非技术岗 6） |
| 人工标注字段 | 20 × 10 = 200 |
| 主实验模型调用 | 20 × 3 版 = 60 |
| 稳定性子实验调用 | 8 × 3 版 × 2 轮 = 48 |
| 模型输出信息单元总数 | 1242（v1 410 / v2 427 / v3 405） |

> **关于样本量**：原设计为 50～100 条。本次因大模型角色由对话内模型逐条扮演、且每条标准答案需人工逐字核对，缩减为 20 条。全部脚本已参数化，接入真实 API 后把 `data/01_clean_sample.py` 中的 `QUOTA` 改为 `{"A_AI技术岗":20,"B_非AI技术岗":40,"C_非技术岗":40}` 即可扩展到 100 条，评测链路无需改动。

## 二、数据集构建（步骤 ①②）

### 2.1 清洗

原始文件为 **GBK 编码**（UTF-8 直接读取会在第 324 字节报 `UnicodeDecodeError`），28 列，3471 行。清洗规则与逐级损耗：

| 步骤 | 规则 | 剩余 |
|---|---|---|
| 原始 | — | 3471 |
| 保留有 JD 正文 | `jd` 非空 | 3046 |
| JD 文本去重 | 同一 JD 在多家公司重复投放 | 2979 |
| 长度过滤 | 180 ≤ len ≤ 700，过短无信息量、过长不利人工标注 | 2389 |
| 乱码过滤 | `?` 替换字符占比 < 0.4%（爬取时的编码丢失，如「支付?业」） | 1200 |

### 2.2 分层与抽样

按岗位技术属性分三层，固定随机种子 `random_state=42`：

- **A 层 AI 技术岗**：JD 命中 `PyTorch|大模型|机器学习|NLP|AI Agent|…` 等 AI 词表 → 总体 20 条，抽 8 条（全取）
- **B 层非 AI 技术岗**：职位名称命中技术岗词表且不在 A 层 → 总体 308 条，抽 6 条
- **C 层非技术岗**：其余（金融销售、理财、管理类）→ 总体 872 条，抽 6 条

三层的设计意图不是代表性，而是**制造不同类型的抽取难点**：A 层考察 AI 技术栈边界，B 层考察高密度技术名词的召回，C 层考察非技术语境下「硬技能/软技能」的划分与大量 null 字段。

### 2.3 送入模型的文本

```
职位：{title}
【职位描述】
{jd_clean}
```

**关键设计**：只注入岗位名称与 JD 正文，**不注入** CSV 中已结构化的 `salary` / `location` / `experience` / `degree` 四列。理由是——若把这些列拼进输入，模型只需原样复制，薪资、地点、学历、经验四个字段的准确率会趋近 100%，实验将失去区分度；只给正文，则这些字段是否出现完全取决于 JD 作者，从而**自然产生大量真实的「未提及」场景**，这正是考察防幻觉能力的关键。实测 20 条样本中，薪资仅 2 条提及、地点仅 2 条提及、学历 15 条、经验 13 条。

## 三、Ground Truth 标注（步骤 ③）

### 3.1 最高原则

> 标准答案中的每一项必须能在原文找到**字面依据**；原文未写的一律 `null` / `[]`，不得用常识补全。

### 3.2 关键消歧规则（完整版见 `data/annotation_guideline.md`）

| 规则 | 内容 | 典型样本 |
|---|---|---|
| R1 | 站点技能标签块属于原文，计入标注并与正文去重 | J04 顶部 17 个标签 |
| R2 | 地点线索 ≠ 工作地点，仅明确声明才填 | J06「工作地点：海淀」填；J10「有意愿在常州地区发展优先」不填 |
| R3 | 「优先」出现在学历/经验上仍填入并保留「优先」字样 | J07「硕士及海外留学背景优先」→ `硕士优先` |
| R4 | 任务名 ≠ 技术名 | J04 的「文本分类/意图识别」不入 AI 技术栈 |
| R5 | AI 技术栈是硬技能的子集，同一项两处都要出现 | J04 的 PyTorch |
| R6 | 大数据 ≠ AI | J11 的 Hadoop/Hive 不入 AI 技术栈 |
| R7 | 标签与正文冲突以正文为准，标签值登记为可接受别名 | J11 标签「2-8年」vs 正文「5年以上」 |

### 3.3 复核结果

单标注员 + 二次自查复核，200 个标注单元中两遍不一致 13 处，**自查一致率 93.5%**。不一致集中于两类：**AI 技术栈边界**（6 处）与 **null 判定**（5 处）。据此新增 R2/R4/R6/R7 并回改全部样本，歧义裁定过程留档于 `data/ambiguous_cases.md`。

### 3.4 数据集中的「陷阱样本」

标注过程中刻意保留了 7 条对防幻觉能力有强区分度的样本：

| 样本 | 陷阱类型 |
|---|---|
| J01 AI实习生 | 岗位名含 AI，但全文无任何具体 AI 技术 → AI 技术栈 GT 为 `[]` |
| J04 算法工程师 | 技术密度极高（22 项硬技能）但**全文无一句软技能表述** → 软技能 GT 为 `[]` |
| J08 web前端 | 学历、经验、薪资、地点四项全部未提及 |
| J13 Java工程师 | 全文未提工作年限 → 经验 GT 为 `null` |
| J17 理财经理 | 只有职责与福利，学历/经验/软技能全部为空 |
| J18 营业部副总 | 「金融等相关专业」是专业限制不是学历 → 学历 GT 为 `null` |
| J11 java工程师 | 标签与正文经验年限冲突 |

## 四、三版 Prompt 设计（步骤 ④，对应论文 3.6 节）

### 4.1 设计逻辑

| 版本 | 策略 | 研究问题 | 长度 |
|---|---|---|---|
| v1.0 | Zero-shot 简单指令 | 建立基线，暴露无约束时的失效模式 | 14 行 |
| v2.0 | 角色设定 + 字段定义 + JSON Schema + 防幻觉规则 | 字段定义与输出格式约束能否提升结构化性能？ | 43 行 |
| v3.0 | Few-shot（含负例）+ 细粒度边界规则 + 输出前自检 | 示例与自检能否进一步提升准确性与稳定性、消除幻觉？ | 128 行 |

三版为**严格增量**关系：v2 = v1 + 角色/定义/Schema/规则，v3 = v2 + 边界细则 + 正负示例 + 自检清单。每一次修改都对应上一版实测暴露的具体失效模式，而非措辞替换。

### 4.2 v2.0 相对 v1.0 的改动动因

v1.0 实测暴露 4 类问题，逐条对应 v2.0 的补丁：

| v1.0 失效模式 | 实测证据 | v2.0 对策 |
|---|---|---|
| 输出格式不统一 | 20 条输出中 19 条非 JSON（编号列表 12、Markdown 表格 2、加粗段落 5） | 给出完整 JSON 模板 + 「只输出 JSON」 |
| 字段边界混淆 | J03 把「深度学习框架（如 TensorFlow/PyTorch）」写进 AI 技术栈 | 逐字段给出定义 |
| 常识补全 | J04「学习能力（AI 岗位通常要求持续跟进前沿技术）」 | 「不允许根据职位名称推测技能」 |
| 「未提及」表述不一致 | 出现「未提及/未说明/未提供/无/招聘信息中未提及/面议」6 种写法 | 统一「未出现的信息填写 null」 |

### 4.3 v3.0 相对 v2.0 的改动动因

v2.0 实测残留 3 类问题：

| v2.0 残留问题 | 实测证据 | v3.0 对策 |
|---|---|---|
| AI 技术栈边界仍不清 | J04 把 7 个 NLP **任务名**写进技术栈；J11 把「大数据/云计算」写进技术栈；J05 把裸标签「ai」写进技术栈 | 增加规则 (b)(c)：任务名不入栈、大数据不入栈 |
| 软技能仍有职责→能力的改写 | J07「汇报能力」「跨条线协同能力」、J10「沟通能力」、J17「客户服务能力」 | 明确「原文没有出现任何软技能表述时必须输出 `[]`」 |
| 学历字段仍会补层次 | J06 原文只写「统招全日制、学信网可查」，v2 补出「本科」 | 明确「专业限制不是学历层次」+ 负例示范 |
| 地点字段过度提取 | J10 把「有意愿在常州地区发展优先」判为工作地点；J18 把标签「全国区域」判为工作地点 | 明确工作地点的声明形式 |

v3.0 另加**负例 Few-shot**（AI 产品实习生 → AI 技术栈必须为 `[]`）与**输出前 5 项自检清单**。

## 五、评测方法（步骤 ⑥⑦⑧）

### 5.1 三级解析与 Schema 校验

```
LLM 原始输出
   ↓ L0 严格 json.loads ......................... strict_valid
   ↓ L1 修复解析（去 ``` 围栏 / 截取首尾花括号 / 去尾逗号 / 中文引号） ... repaired_valid
   ↓ L2 自由文本启发式解析（专为 v1.0 兜底）............ text_parsed
   ↓ Schema 校验（7 顶层字段齐备、薪资与技能为嵌套对象、三列表字段确为数组）
   ↓ 字段标准化（归一化 + 别名表）
   ↓ 指标计算
```

Schema 用 `dataclass` 实现（等价于 Pydantic 的 `BaseModel`，避免引入外部依赖）：

```python
@dataclass
class JobInfo:
    职位名称: Optional[str] = None
    最低薪资: Optional[str] = None
    最高薪资: Optional[str] = None
    薪资周期: Optional[str] = None
    工作地点: Optional[str] = None
    硬技能: List[str] = field(default_factory=list)
    软技能: List[str] = field(default_factory=list)
    学历要求: Optional[str] = None
    经验要求: Optional[str] = None
    AI相关技术栈要求: List[str] = field(default_factory=list)
```

**JSON 有效率**定义为

\[
JSON\ Validity = \frac{成功严格解析的输出数}{模型输出总数}
\]

### 5.2 字段级准确率

10 个原子字段（薪资拆为 3 个子字段，技能拆为硬/软 2 个），20 条样本共 200 个待评价单元：

\[
Accuracy = \frac{正确提取的字段数}{总字段数} = \frac{正确数}{200}
\]

- 标量字段：归一化后与 GT 主值或**可接受答案集**（`eval/accept_sets.json`）匹配即算正确；
- 列表字段（严格口径）：集合完全相等才算正确；
- 列表字段（宽松口径）：\( F1 \ge 0.8 \) 即算正确。

两种口径同时报告，因为严格集合相等对长列表过于苛刻（J04 硬技能有 22 项，错一项即判全错）。

### 5.3 列表字段的 P / R / F1

对硬技能、软技能、AI 技术栈三个列表字段：

\[
Precision=\frac{TP}{TP+FP},\quad Recall=\frac{TP}{TP+FN},\quad F1=\frac{2PR}{P+R}
\]

同时报告 micro（合并全部样本的 TP/FP/FN）与 macro（逐样本 F1 后取均值）。

### 5.4 幻觉率：两阶段判定

**阶段 1（自动初筛）**：把模型输出拆成「信息单元」（每个列表元素 + 每个非空标量），对每个单元在归一化后的招聘原文中做字面证据检索。检索命中即判有依据；未命中进入人工裁定队列。三版共 1242 个单元，89 个进入队列。

**阶段 2（人工裁定，H-Rule）**：

1. 硬技能 / AI 技术栈 / 标量字段：原文出现即 `SUPPORTED`，压缩改写亦可；
2. **软技能字段追加一条**：若其依据仅出现在「岗位职责」段而被模型改写为能力要求，判为「职责→能力」**过度推断，计入幻觉**；
3. 自动初筛未命中且不在裁定表中者，默认计为幻觉。

规则 2 是本实验的关键判据。例如 J08 原文职责写「与后端工程师沟通协作，调试数据接口」，模型据此输出软技能「沟通能力」——文本里确有「沟通」二字，但招聘方从未把它列为对候选人的能力要求，这正是典型的合理但原文不存在的补全。裁定结果全部留档于 `eval/semantic_support.json`（含证据出处）。

\[
Hallucination\ Rate_{unit} = \frac{无原文依据的信息单元数}{模型生成的信息单元总数}
\]

\[
Hallucination\ Rate_{sample} = \frac{存在幻觉的样本数}{样本总数}
\]

### 5.5 运行时间

**本次实验未能取得真实 API 延迟**：大模型角色由对话内模型扮演，不存在网络往返与服务端排队，直接计时无意义。因此报告两个层次的量：

- **Token 消耗（实测量）**：按「中文字符 ≈ 1 token，其余字符 ≈ 1/4 token」统计输入与输出 token；
- **运行时间（估算量）**：按显式延迟模型换算

\[
T = T_{overhead} + \frac{N_{in}}{v_{prefill}} + \frac{N_{out}}{v_{decode}}
\]

其中 \( T_{overhead}=0.35\,\mathrm{s} \)，\( v_{prefill}=3000\ \mathrm{tok/s} \)，\( v_{decode}=42\ \mathrm{tok/s} \)，取自中等规模模型的公开典型值。**这三个参数是假设值而非本实验测得**，因此下文表格中的耗时一律标注「估算」。`experiments/run_llm.py` 已在调用处埋好计时点，接入真实 API 后可直接产出实测值：

```python
t0 = time.time()
text, tin, tout = call_llm(prompt, model, temperature)
t1 = time.time()
runtime = t1 - t0
```

### 5.6 输出一致率

固定模型、样本、Prompt，独立重复生成 3 次：

\[
Consistency = \frac{重复运行中三次取值完全一致的字段数}{总字段数}
\]

子样本 8 条 × 10 字段 = 80 个字段。

## 六、实验结果（对应论文 3.8 节）

### 6.1 主结果表

| Prompt 版本 | 字段提取准确率 | Hallucination 率 | 平均运行时间 | 输出一致率 | 优化建议 |
|---|---:|---:|---:|---:|---|
| **v1.0** Zero-shot | **78.5%** | **8.05%** | 5.05 s（估算） | **57.5%** | 增加字段定义与 JSON 输出格式约束 |
| **v2.0** 角色+定义+Schema | **91.0%** | **1.17%** | 4.94 s（估算） | **78.8%** | 增加 Few-shot 负例与 AI 技术栈边界细则 |
| **v3.0** Few-shot+自检 | **98.0%** | **0.00%** | 5.09 s（估算） | **100.0%** | 配合 Schema 校验层，并将 temperature 固定为 0 |

带 95% Wilson 置信区间的版本：

| 版本 | 字段准确率（严格） | 字段准确率（宽松） | 幻觉率（单元级） | 幻觉率（样本级） | 输出一致率 |
|---|---|---|---|---|---|
| v1.0 | 78.5% [72.3, 83.6] | 88.0% | 8.05% [5.79, 11.09] | 65.0% | 57.5% [46.6, 67.7] |
| v2.0 | 91.0% [86.2, 94.2] | 94.5% | 1.17% [0.50, 2.71] | 20.0% | 78.8% [68.6, 86.3] |
| v3.0 | 98.0% [95.0, 99.2] | 99.5% | 0.00% [0.00, 0.94] | 0.0% | 100.0% [95.4, 100] |

> v3.0 的 0% 幻觉应读作「在 405 个信息单元中未观测到幻觉」，按规则三，真实幻觉率的 95% 置信上界为 **0.74%**，并非真的为零。同理 100% 一致率的置信下界为 95.4%。

### 6.2 JSON 有效率与 Schema 通过率

| 版本 | 严格解析成功 | 修复后可解析 | Schema 完全通过 | 非 JSON 输出 |
|---|---:|---:|---:|---:|
| v1.0 | **5.0%** | 5.0% | 0.0% | 19 / 20 |
| v2.0 | **90.0%** | 100.0% | 100.0% | 0 / 20 |
| v3.0 | **100.0%** | 100.0% | 100.0% | 0 / 20 |

v2.0 的 10% 严格失败全部来自 Markdown 代码围栏（```json … ```），修复层可 100% 挽回；v3.0 因显式写明「不输出任何 Markdown 代码块标记」而消除该问题。v1.0 的 19 条自由文本必须依赖启发式文本解析器才能进入评测——**这本身就是最有力的证据：没有格式约束时，下游自动化统计根本无法建立**，且启发式解析器会引入自身错误（如把「数据分析工具（如 Excel/SQL）」误切成两项）。

### 6.4 列表字段 P / R / F1（micro）

| 版本 | 字段 | P | R | F1 | TP | FP | FN |
|---|---|---:|---:|---:|---:|---:|---:|
| v1.0 | 硬技能 | 0.927 | 0.886 | 0.906 | 241 | 19 | 31 |
| v1.0 | 软技能 | 0.656 | 0.913 | **0.764** | 42 | 22 | 4 |
| v1.0 | AI 技术栈 | 0.500 | 0.464 | **0.481** | 13 | 13 | 15 |
| v2.0 | 硬技能 | 0.982 | 0.989 | 0.985 | 269 | 5 | 3 |
| v2.0 | 软技能 | 0.902 | 1.000 | 0.949 | 46 | 5 | 0 |
| v2.0 | AI 技术栈 | 0.667 | 1.000 | **0.800** | 28 | 14 | 0 |
| v3.0 | 硬技能 | 0.982 | 0.989 | 0.985 | 269 | 5 | 3 |
| v3.0 | 软技能 | 1.000 | 1.000 | 1.000 | 46 | 0 | 0 |
| v3.0 | AI 技术栈 | 1.000 | 1.000 | 1.000 | 28 | 0 | 0 |

值得注意的是 **v2.0 的 AI 技术栈：召回率 1.000 而精确率仅 0.667**。说明 v2.0 已经能把该找的都找出来，问题完全出在「多找」——14 个 FP 全部是边界误判（7 个 NLP 任务名、2 个大数据技术、1 个裸标签「ai」、2 个泛化词「算法模型/算法设计」、2 个云计算）。这直接决定了 v3.0 的改进方向应当是**收紧定义而不是增强提取能力**，也是 v3.0 只加了三条边界规则就把 F1 从 0.800 推到 1.000 的原因。

### 6.5 Token 消耗与耗时

| 版本 | 平均输入 Token | 平均输出 Token | 合计 | 相对 v1.0 | 平均耗时（估算） |
|---|---:|---:|---:|---:|---:|
| v1.0 | 405 | 192 | 596 | 1.00× | 5.05 s |
| v2.0 | 720 | 183 | 902 | 1.51× | 4.94 s |
| v3.0 | 1719 | 175 | 1894 | 3.18× | 5.09 s |

一个反直觉但可解释的观察：**v3.0 的 Prompt 长了 4.2 倍，端到端耗时却几乎没变**。原因是在自回归推理中，输入侧走并行 prefill（约 3000 tok/s），输出侧走串行 decode（约 42 tok/s），耗时由输出长度主导；而约束越强，模型输出越紧凑（192 → 175 token），恰好抵消了 prefill 的增量。

因此 trade-off 的准确表述应当是：

> **Prompt 复杂度提升带来的主要成本是 Token 计费（3.18 倍），而非推理延迟。** 在按 token 计费的场景下 v3.0 成本显著更高；在延迟敏感的场景下 v3.0 几乎不吃亏。

如需压缩成本，可对 v3.0 做两点工程优化：把 128 行系统指令放入 **Prompt Caching**（多数厂商对缓存命中部分按 10% 计价），或改用 **batch 接口**（通常 50% 折扣）。

### 6.6 重复运行稳定性（3 次独立生成，8 条子样本）

| 版本 | 一致字段数 | 输出一致率 |
|---|---:|---:|
| v1.0 | 46 / 80 | **57.5%** |
| v2.0 | 63 / 80 | **78.8%** |
| v3.0 | 80 / 80 | **100.0%** |

逐字段一致率：

| 字段 | v1.0 | v2.0 | v3.0 |
|---|---:|---:|---:|
| 职位名称 | 75% | 100% | 100% |
| 薪资三字段 | 100% | 88% | 100% |
| 工作地点 | 75% | 100% | 100% |
| 学历要求 | 25% | 100% | 100% |
| 经验要求 | 25% | 50% | 100% |
| 硬技能 | **12%** | **38%** | 100% |
| 软技能 | **12%** | 75% | 100% |
| AI 技术栈 | 50% | 62% | 100% |

**三个可直接写进论文的观察**：

1. **波动集中在列表字段**。v1.0 的硬技能与软技能一致率只有 12%（8 条样本里仅 1 条三次完全一致）。以 J09 硬技能为例，三次输出分别为「小程序 / Web端 / 前端开发」「…+ 小程序开发」「小程序开发 / Web前端开发」——技能项本身没错，波动的是**粒度与表述**，而这足以让下游的词频统计、技能共现网络产生系统性偏差。

2. **v2.0 出现了一个反常点：薪资一致率从 100% 掉到 88%**。原因是 v2.0 只说「提取最低薪资、最高薪资、薪资周期」而未规定格式，J19 三次分别输出 `"15000元"/"月"`、`"15000"/"元/月"`、`"15000元"/"月"`。v3.0 通过两个薪资示例（`20-30K·14薪` 与 `15000-30000元/月`）钉死了写法，一致率回到 100%。**这说明字段定义与格式示例是两件事，前者不能替代后者。**

3. **经验要求是 v2.0 最不稳的标量字段（50%）**。原因是「优先」类表述没有明确处理规范，模型时而填入时而置 null（如 J01「有实习经验者优先」、J17「通过证券从业资格考试者优先」）。v3.0 显式规定了「优先」的处理方式后达到 100%。

### 6.7 误差与幻觉归因

三版共 38 个幻觉单元，按字段分布：

| 字段 | v1.0 | v2.0 | v3.0 |
|---|---:|---:|---:|
| 软技能 | **20** | **4** | 0 |
| AI 技术栈 | 5 | 0 | 0 |
| 硬技能 | 4 | 0 | 0 |
| 学历要求 | 2 | 1 | 0 |
| 经验要求 | 1 | 0 | 0 |
| 职位名称 | 1 | 0 | 0 |
| **合计** | **33** | **5** | **0** |

**软技能贡献了 v1.0 全部幻觉的 60.6%、v2.0 的 80%**，是最顽固的幻觉来源。典型案例：

- J04（22 项硬技能、全文无一句软技能表述）→ v1.0 补出「良好的沟通能力」「团队协作能力」「学习能力（AI 岗位通常要求持续跟进前沿技术）」。第三项模型甚至把推理依据写在了输出里——「AI 岗位通常要求」正是常识补全的自白。
- J13、J17、J19（原文均无软技能表述）→ v1.0 分别补出「团队协作能力/责任心」「沟通能力/客户服务意识/团队管理能力」「沟通能力/客户服务能力/销售能力」。

**机理**：软技能在招聘文本中是高频共现的模板化表述，模型的语言先验极强；一旦缺少「空列表也是合法答案」的明示，模型会默认「招聘信息一定有软技能要求」而据先验填充。v3.0 的对策——**显式写明「原文没有出现任何软技能表述时，必须输出 `[]`」**——是三版改动中单点收益最大的一条。

其余典型幻觉：

| 类型 | 案例 | 版本 |
|---|---|---|
| 补全同类技术 | J03 原文无 Spark/TensorFlow/PyTorch，v1.0 全部补出 | v1.0 |
| 补全知名库名 | J02 补出「Scikit-learn」 | v1.0 |
| 补全学历层次 | J06 原文只写「统招全日制、学信网可查」，v1/v2 均补出「本科」 | v1.0, v2.0 |
| 补全岗位全称 | J06 岗位名原文就是「Java」，v1.0 写成「Java（Java开发工程师）」 | v1.0 |
| 编造缺省值 | J13 经验要求写成「未明确说明（一般要求1-3年）」 | v1.0 |
| 职责→能力改写 | J07「汇报能力」「跨条线协同能力」 | v1.0, v2.0 |

### 6.8 v3.0 的残余误差（4 处）

v3.0 仍有 4 个字段未达严格相等，全部集中在硬技能：

| 样本 | 现象 | 归因 |
|---|---|---|
| J01 | 多出「数据分析工具」 | GT 认为它与「数据分析」重复，模型认为是独立标签项——**标注粒度分歧**，非模型错误 |
| J07 | 漏「售前解决方案」 | 模型输出了「售前技术支持」与「解决方案编写」两个更贴近原文的项，GT 另立了一个合成项——**GT 粒度问题** |
| J09 | 输出「Web端/前端开发/小程序」，GT 为「Web前端开发/小程序开发」 | 模型忠实保留标签原文，GT 做了合并归一——**标注粒度分歧** |
| J18 | 多出「全国区域」 | 该项确为原文标签，但语义上是业务覆盖范围而非技能——**GT 边界判断可商榷** |

四处全部是**标注粒度而非模型能力**问题。这提示一个方法论结论：**当准确率进入 98% 区间后，评测的瓶颈已经从模型转移到标注规范的粒度定义**；若要继续区分模型优劣，必须先把列表字段的粒度规则（是否拆分复合标签、是否合并同义标签）写死到标注规范中。

## 七、Temperature 敏感性实验（未取得实测数据）

原技术路线包含固定 v3.0、改变 `temperature ∈ {0, 0.3, 0.7, 1.0}` 的参数稳健性实验。**本次实验未能完成这一维度**：temperature 是 API 采样层参数，而本实验中大模型角色由对话内模型扮演，无法设定该参数。**报告中不提供任何该维度的数字**，以免与实测数据混淆。

完整实验协议与可执行脚本已备好（`experiments/run_temperature.py`）：

- 固定：Prompt v3.0、同一模型、同一批 8 条子样本、`top_p=1.0`
- 变量：`temperature ∈ {0, 0.3, 0.7, 1.0}`
- 每档重复 5 次，共 \( 8\times4\times5=160 \) 次调用
- 观测：字段准确率、幻觉率、输出一致率、JSON 有效率

```bash
export LLM_API_KEY=sk-xxx
python3 experiments/run_temperature.py --repeats 5
```

待检验的假设（应作为假设写入论文，不得提前认定结论）：

> H1：对结构化信息抽取任务，temperature 上升会降低输出一致率；
> H2：temperature 上升会提高幻觉率，因为采样随机性会放大模型的语言先验；
> H3：v3.0 的强约束能部分抵消高 temperature 的负面影响，即约束越强，性能对 temperature 越不敏感。

H3 是本实验已有数据能给出**间接旁证**的一条：在完全相同的生成条件下，约束越强的 Prompt 三次重复的一致率越高（57.5% → 78.8% → 100.0%），说明 Prompt 约束本身就是一种降低输出方差的手段。但这只是旁证，不能替代 temperature 实验。

## 八、结论与 Prompt 优化策略

### 8.1 主要结论

1. **格式约束的收益最陡峭**。v1.0 → v2.0 仅增加角色设定、字段定义与 JSON 模板，JSON 严格有效率就从 5% 跃升到 90%，字段准确率 +12.5 个百分点，幻觉率下降 85%。对工程落地而言，这一步是性价比最高的投入。

2. **Few-shot 的价值主要在边界消歧，不在提取能力**。v2.0 的 AI 技术栈召回率已达 1.000，v3.0 的提升全部来自精确率（0.667 → 1.000）。这说明当模型已经「找得全」之后，Prompt 优化的重点应转向**告诉它什么不算**，而负例示范比正例更有效。

3. **防幻觉的关键是给「空」一个合法地位**。幻觉的主体（60.6%）来自软技能字段的模板化补全，而消除它靠的不是「不许编造」这类泛化指令（v2.0 已有类似规则却仍有 4 处），而是「**原文没有软技能表述时必须输出 `[]`**」这样把空值显式合法化的具体规定。

4. **稳定性与准确性同向提升，但受不同因素驱动**。准确性主要由字段定义驱动，稳定性主要由**格式示例**驱动——v2.0 有薪资字段定义却无格式示例，薪资一致率反而从 100% 掉到 88%，v3.0 补上两个写法示例后回到 100%。

5. **复杂 Prompt 的代价是 Token 而非延迟**。v3.0 Token 消耗为 v1.0 的 3.18 倍，端到端耗时却基本持平（输出侧 decode 主导，且强约束反而缩短输出）。

6. **98% 之后的瓶颈是标注规范**。v3.0 残余的 4 处误差全部是标注粒度分歧而非模型错误。

### 8.2 可复用的 Prompt 优化策略清单

| 优先级 | 策略 | 依据 |
|---|---|---|
| P0 | 给出完整 JSON 输出模板并声明「只输出 JSON、不要 Markdown 围栏」 | JSON 有效率 5% → 100% |
| P0 | 为每个字段写明确定义，尤其是易混字段的**互斥边界** | 硬/软技能 F1 大幅提升 |
| P0 | 把空值显式合法化：「原文未出现时必须输出 `null` / `[]`」，并配一个空值负例 | 消除 60.6% 的幻觉来源 |
| P1 | 用负例 Few-shot 界定「什么不属于该字段」（任务名 ≠ 技术栈、大数据 ≠ AI、专业限制 ≠ 学历） | AI 技术栈 P 0.667 → 1.000 |
| P1 | 为每个可能有多种写法的字段提供 1～2 个**格式示例**（不只是定义） | 薪资一致率 88% → 100% |
| P1 | 明确「优先/加分项」的处理规范 | 经验要求一致率 50% → 100% |
| P2 | 输出前自检清单（逐字段核对原文依据） | 与 P0/P1 协同 |
| P2 | 固定 `temperature=0`、`top_p=1`，支持 `seed` 的服务端固定 seed | 待 §7 实验验证 |
| P2 | 在 LLM 之后加程序化 Schema 校验层，不合法则重试 | 修复层可挽回 v2.0 全部 10% 的围栏失败 |
| P2 | 长系统指令走 Prompt Caching / batch 接口 | 抵消 3.18 倍 Token 成本 |

### 8.3 局限性

1. **样本量**：N=20（200 字段级单元），置信区间较宽（如 v3.0 准确率 95% CI 为 [95.0%, 99.2%]）。扩展到 100 条可把区间宽度压缩约一半。
2. **单标注员**：未做双人标注与 Cohen's Kappa，标注偏差无法量化；二次自查一致率 93.5% 只是自身可靠性的下界估计。
3. **运行时间为估算值**：延迟模型的三个参数是假设值，需在真实 API 上标定。
4. **Temperature 维度缺失**：见 §7。
5. **单模型**：未做跨模型对比，结论对特定模型族的依赖程度未知。三版 Prompt 的相对排序预期稳健，但绝对数值会随模型变化。
6. **领域偏斜**：抽样总体以金融/证券行业岗位为主，A 层 AI 技术岗在清洗后总体中仅 20 条（1.7%），已全部取用，无法再扩充。

## 附录 C：关于本次实验中「大模型角色」的说明

按约定，本实验中的大语言模型角色由对话内模型扮演，即三版 Prompt 下的 108 条输出均为该模型依据对应 Prompt 真实生成，未经人工编造或事后修饰，原始文本原样落盘于 `outputs/run*_v*_raw.json`。基于这些输出计算的**准确率、P/R/F1、幻觉率、JSON 有效率、Token 消耗、输出一致率均为实测值**。

两处非实测量已在正文标注：

- **运行时间**为按 §5.5 延迟模型换算的**估算值**，参数为假设值；
- **Temperature 敏感性实验**未取得数据，仅提供协议与脚本。

由于同一模型既扮演被测对象又参与标注复核，存在潜在的**评测者—被测者同源偏差**：模型对原文的理解方式可能与其标注 GT 时的理解方式一致，从而系统性高估准确率。缓解措施是标注在前、生成在后且严格依照书面规范执行，并保留全部歧义裁定记录供第三方复核；根本解决办法是在真实 API 上用**另一个模型族**重跑生成环节，标注保持不变。
